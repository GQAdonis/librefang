## Follow-up: shared memory storage embedding dimension

Branch `fix/shared-memory-embedding-dim`, off `merge/upstream-2026-09-27`, by bossfang-feature-steward.

Root cause, from surreal-memory `b7e2093` (`crates/surreal-memory/src/storage/surreal.rs`):

- `SurrealStorage::new` sizes the `entity` and `memory` HNSW indexes from `EmbeddingService::dimensions()`, bails on 0, rebuilds the indexes when the dimension changes on an empty store, and refuses to open when stored vectors have another dimension.
- `add_memory` always overwrites `Memory::embedding` with the storage's own `embed_text(content)`, and `search_memories` embeds the query the same way for its KNN.
  So the storage's embedder is load-bearing for every write and every non-vector recall; the old `NoopEmbedding` doc comment ("real embeddings are supplied at query time") was wrong, and a 0-dimension no-op could never have worked, whatever the guard.

How the rest of the system decides the dimension: `[memory] embedding_dimensions` overrides, otherwise the runtime's `infer_dimensions(embedding_model)` (`crates/librefang-runtime/src/embedding.rs`), both surfaced as `EmbeddingDriver::dimensions()`.
`librefang-memory` cannot depend on `librefang-runtime`, so the dimension comes from the caller, which is not a product decision.

The fix:

- `open_shared_memory_storage(storage_cfg, embedding, dimensions)` now takes the embedding driver (as `Arc<dyn EmbeddingFn>`, the existing runtime-to-memory bridge trait) and its dimension, and adapts them to surreal-memory's `EmbeddingService`.
- A zero dimension is an explicit error before any store is created; there is no embedding-less mode, because the storage embeds every write.
- The adapter rejects a vector whose length differs from the declared dimension, so a misconfigured `embedding_dimensions` fails with the cause rather than at the HNSW index.
- `SurrealSemanticBackend::open_with_storage` and `SurrealProactiveMemoryBackend::open_with_storage` take and forward the same pair.

Whether the kernel reaches this path: it does not.
Neither backend factory has a caller outside `librefang-memory` and its tests.
`boot.rs` matches `[memory] vector_backend` against `"http"`, `"sqlite"` and `""` only, so `"surreal"` fails boot with "Unknown vector_backend" and unset keeps the SQLite semantic store, while `semantic_backend_name()` reports `"surreal"` for both.
In `vector_backend_boot_test.rs`, the `#[ignore]`d `vector_backend_surreal_boot_selects_surreal_backend` would fail at boot if run, and the auto-mode test would pass only because it checks that name, not the backend in use.
Wiring the Surreal semantic backend into boot (passing `embedding_driver` and its `dimensions()`) is a kernel change, left for a separate PR.

`auth_level` choice in `516c9e180`: **confirmed**.
It matches `SurrealConnectionPool::open` (`crates/librefang-storage/src/pool.rs`): `Root` for the `root` user, `Namespace` with the remote namespace otherwise, and the memory config keeps the operational namespace (only the database becomes `memory`).
Embedded passes no credentials, so surreal-memory skips sign-in and the level is inert.
One correction in the same function: an unset or empty password env var used to open an unauthenticated remote session, while the pool refuses with `MissingCredential`; it now errors naming the env var, and always passes the username, as the pool does.

BossFang-surface fixes in `3b231b5d0`: **confirmed**.

- `sandbox_component.rs`: the import move to the `wasmtime_wasi_http` crate root is a pure path change.
- `uar_supervisor.rs`: `Arc::clone(&config_ref())` takes an owned snapshot and releases the `arc_swap` guard before the `.await`, which is correct.
- `surreal_session.rs`: `parent_session_id` is carried through load and save, and omitting `None` optionals from the `.content()` document stores NONE, which `option<string>` accepts; a malformed parent is dropped as the SQLite path does.

Tests:

- `surreal_vector_integration_test.rs::shared_memory_storage_opens_once_and_can_be_shared_by_backends` is un-ignored: it needs only a temp dir, and the CI lane that was supposed to run it runs without `--ignored`.
- New `shared_memory_storage_rejects_zero_embedding_dimension` (fails before the store directory is created) and `shared_memory_storage_round_trips_through_configured_embedder` (embedded store, `add_memory` then `search_memories` through the HNSW index with an 8-dimensional deterministic embedder; `surreal-memory` added as a dev-dependency of `librefang-memory` for it).
- New `shared.rs` unit tests `bridge_reports_declared_dimension_and_passes_matching_vectors` and `bridge_rejects_vectors_of_another_dimension`.
- `surreal_semantic.rs::knn_hnsw_relevance` stays `#[ignore]`d; it now passes a lookup embedder and uses vectors below surreal-memory's 0.92 dedup threshold.

Found, not fixed here (reported for the storage owner):

- `SurrealSemanticBackend` runs `knn_recall`, `forget`, `count` and `get_embeddings` on the operational pool session, but `add_memory` writes to the separate memory store (`librefang-memory.surreal` embedded, database `memory` remote), so those four never see stored memories; `knn_hnsw_relevance` cannot pass until they use the memory store's connection.
- `SurrealSemanticBackend::remember` and `VectorStore::insert` cannot write at all on surreal-memory `b7e2093`: they nest librefang fields under `metadata.librefang`, and SurrealDB rejects them (`Found field 'metadata.librefang', but no such field exists for table 'memory'`) because surreal-memory's v8 migration makes `memory.metadata` FLEXIBLE with `DEFINE FIELD IF NOT EXISTS`, a no-op on the field v1 already defined.
  The fix belongs in surreal-memory (`DEFINE FIELD OVERWRITE`), so the round-trip test above goes through the storage directly.
  The backend also maps storage errors with `e.to_string()`, which keeps only the outermost anyhow context (`add_memory`); the cause above surfaced only with `{e:#}`.
- `remember`'s caller-supplied embedding is discarded by surreal-memory's `add_memory`, which has no API for a precomputed vector; with the same driver on both sides the result is the same vector, computed twice.
