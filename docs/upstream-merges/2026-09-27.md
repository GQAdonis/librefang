Code changes the upgrade required:

- `crates/librefang-memory/src/backends/shared.rs`: surreal-memory's `SurrealConfig` gained `auth_level` (its scoped-credentials work).
  Embedded uses `Root`; remote uses the same rule as `librefang_storage::pool` (`root` user signs in at root level, any other user at namespace level), so the two stores agree on the shared `[storage.backend]` credentials.
  Before this, surreal-memory always signed in at root level, which fails for a namespace-scoped user.
- Nothing else: the SurrealDB 3.3 SDK changes surreal-memory reviewed (futures `Send` but no longer `Sync`, `UPDATE … WHERE` ordering, some `vector::` functions) did not surface in this workspace under clippy with all targets.

surreal-memory's own 3.3 work, for context: it retries `QueryError::TransactionConflict` on every write (3.3 raises it on HNSW-indexed tables), and shares one `Surreal<Any>` rather than cloning per call, because in SDK 3.x a clone is a new server-side session.
BossFang's operational tables define no HNSW or MTREE index, so the conflict-retry concern does not apply to `librefang-storage` writes.
Each BossFang backend clones the client once at construction, not per call.

Operational note: embedded datastores are migrated in place, one way, the first time a 3.3.0 client opens them, and the 3.3.0 server does the same to a 3.2.x data directory.
Back up the embedded `librefang.surreal` / `librefang-memory.surreal` directories, or snapshot the SurrealDB PVC, before the first 3.3.0 start if a rollback must stay possible.
