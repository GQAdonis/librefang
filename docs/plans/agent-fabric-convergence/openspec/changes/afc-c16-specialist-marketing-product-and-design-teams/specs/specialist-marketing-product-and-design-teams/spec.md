# Spec Delta

## Purpose

Define the cross-product behavior for specialist, marketing, product and design teams so compatible implementations preserve the architecture and authority boundaries.

## ADDED Requirements

### Requirement: Task-led specialist selection

Team creation MUST explain the smallest useful role set, a single-agent alternative, skill choices, output contracts and model/cost tradeoffs.

#### Scenario: 1 — Task-led specialist selection

- **WHEN** An inexperienced user requests a coding, marketing, product or full-design task
- **THEN** the guide proposes accountable roles and reviewed skills with separate evaluator assignments and explicit write limits.

### Requirement: Role scope is not authority

UI/UX, mobile, security, product, documentation and code-review roles MUST have explicit evidence and action scopes; titles MUST NOT grant publication, communication or compliance certification authority.

#### Scenario: 2 — Role scope is not authority

- **WHEN** A security or product specialist recommends an external action
- **THEN** the resulting artifact distinguishes advice from verified evidence and the action follows the separate governing grant.

### Requirement: Report acceptance coverage

The implementation MUST satisfy all assigned report acceptance clauses below; source-gap reclassification by C01 requires a recorded equivalent or superseding contract.

- REC-038: UI/UX, mobile, security, product, documentation and code-review presets have bounded assignments and role-specific acceptance.
- REC-047: Representative task produces accepted artifact with independent review and measured cost versus single-agent baseline.

#### Scenario: Supported-profile acceptance

- **WHEN** this capability is evaluated for a supported profile
- **THEN** the acceptance evidence identifies each applicable clause above, the exact source/policy/dependency revisions and the observed outcome; any unproven mandatory clause keeps that profile unsupported.

### Requirement: Customer-priority preset delivery

The first supported team preset MUST enable a coding worker/reviewer journey in Work through accepted C03/C09 contracts and existing skill bindings. Reusable coding and product/design configuration SHALL follow, with other practical presets delivered subsequently. Unused connectors, the BossFang MiniApp and completion of every C15 adapter MUST NOT be prerequisites for the initial coding journey. Customer-feedback presets retain their C10 GitHub workflow dependency. Partial preset evidence MUST NOT complete the broader original role/template tasks or comparative benchmark obligations.

#### Scenario: Coding preset without connector configuration

- **WHEN** a user with no Notion, Slack, Jira or BossFang configuration chooses the coding preset
- **THEN** the supported local team journey remains usable with explicit workspace/write limits, selected models, output contracts and reviewer findings; absent unrelated integrations do not block it.
