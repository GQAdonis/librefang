## Supported command boundary and prerequisite

The installed Delivery Cadence `publication` state machine supports `replace`, `attempt`, `dispatch-result`, `reconcile`, `acceptance`, `status`, and `capabilities`. A `reconcile` needs an existing attempt ID and correlation ID; validated effect receipts must match that attempt, the obligation's candidate and content-manifest digest, version, exact source refs, and downloaded-byte/site proof. None exists for either old obligation. An `attempt` requires a declared consumer adapter with all six evidenced capabilities (`immutableSourceDispatch`, `externalCorrelation`, `artifactProvenance`, `targetSerialization`, `expectedPredecessorPromotion`, `siteReceipts`). The current profile has no declared `publication.adapters`, and an unsupported consumer is `capability-blocked` and cannot acquire credit. Creating a fictional dispatch acknowledgement for an already-directly-dispatched workflow would violate this contract.

An explicit `publication replace` is supported only for an **unstarted** pending obligation, with operator authority, reason, ancestry/compatibility evidence and a **successful Cadence delivery candidate whose recorded scope retains every old task/change/phase**. The command does not itself prove that a selected candidate is a newer released source; the evidence and publication receipt must do that. Current state contains no successful newer candidate covering the C14.1–4 obligation; C10's latest matching candidate is its original `af01868a` (earlier matching candidates do not change this). The 2.2.25 release is not a new Cadence delivery/candidate, so it cannot be substituted through `replace` without fabricating a delivery or expanding scope.
