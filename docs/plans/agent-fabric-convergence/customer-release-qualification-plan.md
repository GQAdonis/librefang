## Failure, correction, and publication rule

If a customer operation fails, record the failing stage and observed error, repair all affected production code/UI/strings/persistence/payload first, then run `pnpm build:mac:arm64` and operate only the failed completed journey on the corrected packaged app. Keep the original failed receipt and source identity. Do not begin the next development increment with a broken customer candidate. A corrected source is a new candidate and needs its own immutable payload/installer provenance.

Keep the existing 120-minute cadence: local Mac ARM64 build and operation every successful delivery; full Mac ARM64/x64 and Windows x64/ARM64 GitHub release, metadata and live website every second successful delivery, and at the final corrected candidate. Publish each ready customer platform without waiting for Intel if its own package and receipts are complete. Linux is outside this customer release. Verify actual downloaded bytes, SHA-256, size, source/architecture and signing against the release manifest; confirm the live site points at those same assets. Keep the previous valid platform link until its replacement is complete.

Cadence's 15 historical successful deliveries, their clocks and source-bound publication debt remain unchanged. The [2.2.25 website receipt](receipts/customer-release-2.2.25-live-website-20261009.json) says publication reconciliation is pending. Clear an obligation only through a supported, matching immutable receipt transition; do not fabricate an acknowledgement for a directly dispatched workflow or increment delivery counts for qualification alone.
