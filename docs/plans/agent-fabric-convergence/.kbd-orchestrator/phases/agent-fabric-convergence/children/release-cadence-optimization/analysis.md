# Analysis: an hourly local Boss delivery cadence

**Stage:** analyze, for operator feedback before plan. This document compares options and recommends a direction. It does not amend C01–C18, register product tasks, mark C08 accepted, or authorize an early integration gate. Source facts are separated from proposed changes below. The [assessment](assessment.md) records the underlying receipts and confidence limits.

## Delivery contract supplied after assessment

Each hourly delivery must finish with a **functioning local `pnpm build:mac:arm64` of The Boss containing the new UAR functionality**. For planning, use elapsed delivery time including waits and build time; record operator waiting separately rather than treating it as agent effort. After that local delivery, ask the operator whether to publish **all macOS and Windows targets now or with the next delivery**; Linux is outside this cadence. Record aggregate agent effort separately from elapsed time. A missed hour is an honest overrun, not an invitation to call incomplete source a release. The first cold Rust/Electron build may exceed an hour; current evidence cannot guarantee otherwise.

The parent plan's 18 changes remain the coverage register. A user-visible increment needs its production core, The Boss UI, typed IPC/host adapter, internationalization, persisted settings/state, applicable governance and workspace isolation, then **one completed-phase integration gate and the actual local application build/launch**. Moving a checkbox into a newly named “phase” does not make partial behavior independently shippable or justify early testing. Only a complete customer journey qualifies.

## Build and artifact boundary: observed source versus proposed adaptation

**Observed source:** `package.json:29–31,45–46` and `scripts/release-platforms.cjs:5–19` route the exact plain `pnpm build:mac:arm64` command to a profile with UAR disabled. `scripts/import-uar-sidecar-payloads.cjs:139–178` requires immutable win32-x64 and darwin-arm64 UAR records at one source revision before it imports canonical installer payloads. `scripts/release-preflight.cjs:16–45` freezes source, version and profile; `.github/workflows/the-boss-release.yml:87–118,203–215` packages/publishes by platform. Therefore running the exact command today cannot meet the new UAR local-delivery criterion. A plain successful DMG is not evidence of a working UAR build.

**Recommended future design, not implemented:** make the exact `pnpm build:mac:arm64` a UAR-enabled **local-delivery profile**. It may use a locally built, checksummed arm64 sidecar payload from a **clean, committed UAR source revision explicitly paired with the separate Boss commit**, written as a clearly labeled local overlay. The local overlay must never masquerade as a canonical release manifest: CI/release preflight rejects it and continues to require both canonical win32-x64 and darwin-arm64 immutable records at the same UAR source SHA. Dirty source cannot be assigned an immutable source revision; commit relevant source before freezing a local delivery. The local artifact receipt records Boss/UAR commits, sidecar hash, app hash, profile, package contents, launch result and supported capabilities. Local-only payload selection must preserve the existing runtime binary path and platform resource layout. The [electron-builder `extraResources` documentation](https://github.com/electron-userland/electron-builder/blob/master/website/docs/contents.md) confirms native executables can be placed outside ASAR in `Contents/Resources` and accessed using `process.resourcesPath`; this supports the packaging location, not the correctness of our proposed overlay.

Release publication is a **separate exact-source promotion**. The user can select “publish now” only after the local Mac journey works. A publish-now run needs native, checksummed payloads and installers for **darwin-arm64, darwin-x64, win32-x64 and win32-arm64**, then GitHub release/site links and installed acceptance by platform. Current UAR-enabled payload/profile support is evidenced only for darwin-arm64 and win32-x64; Mac Intel and Windows ARM64 require production implementation and native payloads before they can be advertised. The two currently supported customer platforms cannot be described as “all macOS and Windows.” A “wait” answer defers publication without downgrading the local build receipt. If publication is selected, its waits and build time remain visible in elapsed delivery time, even when work on the next increment can safely overlap.

## Cadence alternatives

| Alternative | Customer feedback speed | Technical consequence | Disposition for later plan |
| --- | --- | --- | --- |
| Local Mac first, then operator chooses publication | Fastest plausible first working UAR/Boss feedback; preserves one exact local command. | Requires a source-frozen arm64 local overlay, functioning packaged launch and honest separation from canonical release; Windows/Intel/ARM are not implicitly certified. | **Recommended** for the local hourly target, subject to operator feedback and the build-profile repair above. |
| Build and publish all four Windows/macOS targets every hour | Immediate public platform parity when it succeeds. | Existing canonical sidecar coupling, two unsupported UAR payload profiles, native installers and publication likely exceed the hour. A failed platform would force truthful partial-release handling. | Do not make this the prerequisite to every local increment; ask for publication after each local delivery. |
| Batch native builds/publication after several local increments | Lower repeated release overhead. | Users outside the Mac development host wait longer; a late cross-platform mismatch may require source changes and a fresh exact-source local build. | Valid only when the operator answers “wait”; retain an explicit published-versus-local gap in the ledger. |

The recommendation optimizes **time to first usable local Boss** while preserving exact platform claims. It is not an assertion that one finished phase can routinely be implemented and built in sixty minutes. The measured Compass cold refresh alone was 134.98 seconds and wrote about 0.88 GB; it does not estimate incremental graph-refresh cost. One local Rust build writer remains the safe default on this 64 GiB, 10-logical-CPU host until measured contention supports a change.

## Ownership, measurement and stage constraints

Parallel work should follow isolated file claims, not matching branch names alone:

- **UAR Rust lane:** team domain, SurrealDB store, existing thread/instance kernel, admission and governance. One owner for each Rust module and one heavy local Rust build writer.
- **Boss product lane:** settings navigation, components, typed IPC/host adapter, persistence schema and every locale for the same journey. It may edit in parallel with Rust while contracts are frozen, but it cannot claim an executable capability before provider support exists.
- **Payload/release lane:** prepare native binary manifests, checksums, local-overlay profile and CI rejection, and later platform jobs/site metadata. It may prepare files while production code is being written; final native compilation/packaging waits for a frozen source snapshot. No edits to that snapshot while its build is running.
- **Ledger/observer lane:** record source-to-gate-to-local-to-published status and delivery timing, with no authority to add tests, rewrite scope, close tasks or declare acceptance. Reuse the existing KBD/team/Karpathy infrastructure; do not create another scheduler or daemon.

At each candidate phase start and end, capture **critical-path elapsed** (including blocked waits, compiler/build, operator decision and publication if selected) and **summed active agent minutes** separately. Also record build/gate duration, source revision, time to first functioning local app, rework from failed gates, and installed customer observation. The current single Karpathy event with `elapsedHours: 0.0` cannot supply these measures. Commit timestamps are not agent-time evidence. A delivery-optimization observer may identify bottlenecks and suggest the next question; it cannot shorten a required gate or authorize a release.

Compass refresh should be a bounded **incremental changed-root queue** using the existing CLI and one graph owner, not a new service or unconditional hourly full reindex. The cold UAR run (8,184 files, 447,259 nodes, 495,392 edges, 134.98 seconds, partial graph with identity collisions) supports positive lookup but not absence claims. Whether incremental refresh is cheap or reliable enough for hourly use remains a measured question for the plan/execute stages.

## Proposed boundary operation details

After the whole shipping increment is implemented, freeze its source and run the actual packaging command. Its required compiler checks and package validator are steps within the single delivery gate, not separate pre-implementation checks. Open the newly produced app with runtime sidecar overrides cleared; confirm the packaged UAR source/version and effective port, then exercise the increment’s real UI operation, persistence and relevant isolation/recovery path. Record the DMG path/hash and running application version. The Mac app must remain available for the operator to use. Do not replace a user’s running app or data during preparation; use a versioned artifact and explicit launch/install handoff.

Ask after EVERY successful delivery: “Publish this version for all macOS and Windows targets now, or wait until the next delivery?” Record the answer against the immutable boundary; no answer keeps publication pending. Continue later approved implementation in another source/output snapshot while a remote publication runs. Use one metadata/site publisher; never regress a newer published platform when an older job finishes. Retain the previous working public artifact until the new platform artifact succeeds. Missing target support is disclosed and remains required work, not silently converted to a non-UAR release.

Local resource admission permits one heavy Rust/Electron packaging writer at a time; other lanes may edit separate sources, design UI or maintain documentation. Do not overlap a second expensive compile or Compass scan with packaging simply because it uses another language. At each active-work hour, queue incremental Compass updates for changed roots, check the graph revision, and query affected symbols. Log the actual update or contention deferral and run it after the current heavy writer; unchanged roots require a freshness check, not reindexing. No recurring daemon or automation is installed during Analyze.

The proposed optimization observer has a small checkpoint-bound observation budget (initial planning suggestion: at most five minutes per hour), reads existing metrics/logs, and returns one prioritized recommendation with evidence, expected gain and a later falsifier. Unknown agent durations stay null/unavailable; do not invent zeros. Production review and verifier roles remain dormant until the complete shipping boundary. This process artifact review is not a production-code gate.
