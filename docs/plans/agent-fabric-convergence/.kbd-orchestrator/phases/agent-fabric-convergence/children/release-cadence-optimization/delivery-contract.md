# Delivery contract: working local Boss, then an explicit platform decision

**Contract stage:** process implementation for `afc-release-cadence-optimization` task 1.1. This document sets acceptance and handoff rules; it does not report a build, installed result, release, or website deployment. Product changes belong to the first subsequent parent shipping increment. The [approved plan](plan.md) and [OpenSpec contract](../../../../../openspec/specs/release-cadence-governance/spec.md) govern its scope.

## What constitutes one local delivery

One delivery is a complete, independently useful journey through **the newly built The Boss application**. The source boundary includes the relevant UAR/core capability, reachable Boss UI and navigation, typed IPC/host adapter, persisted settings and runtime state, every shipped locale, the applicable current governance/approval boundary, and isolation of two workspaces where the feature handles workspace data. UI that advertises an unsupported UAR capability, or a sidecar that cannot be reached from the UI, is incomplete. A catalog-only screen is not a default release; the first team delivery must operate a bounded team unless the operator expressly accepts catalog management as useful by itself.

The owner finishes all production wiring before the one phase-end integration gate. That single gate first runs the **exact local command `pnpm build:mac:arm64`**, then opens the resulting Apple Silicon application and exercises the real packaged product path and new user action. Required compiler/packager checks within that build are part of the boundary. If the gate or launch fails, fix the observed failure and rerun only the failed completed-phase gate/build. A source commit, `cargo check`, unit/mock test, DMG checksum or sidecar-only query does not substitute for a functioning Boss journey. Do not run tests, standalone verification builds or review loops while production wiring remains incomplete.

The local app must launch its **packaged** UAR helper from its own resources with `THE_BOSS_UAR_SIDECAR_PATH` and equivalent developer overrides cleared. Record helper source/version, effective port and health/capability response, then perform the increment's actual UI operation and observe its persisted result after an application/runtime restart when that feature promises recovery. For workspace-scoped operations, demonstrate two workspaces with distinct data/authority and no cross-scope leakage. Preserve the user's existing installed app, data and running processes while preparing the versioned artifact; provide an explicit launch/install handoff rather than silently replacing them.

### Local payload provenance proposed for the first parent delivery

The current exact Mac command disables UAR, while the canonical importer requires immutable Windows x64 **and** Mac ARM64 UAR records at one UAR source SHA. The first parent shipping increment therefore owns a product-code repair: make `pnpm build:mac:arm64` a UAR-enabled local delivery, using a **local-only arm64 payload record** that contains archive/file SHA-256 values, architecture, and a clean committed UAR revision paired with the separately committed Boss revision. It must stage the executable in the physical app resources path outside ASAR. A developer runtime path override cannot make a payload count as packaged. Dirty UAR or Boss source must be committed before source freeze; a `HEAD` label over changed code is not immutable provenance.

The local record is an explicitly marked overlay, not a public release manifest. Public CI/release preflight must reject this overlay and continue to require the two canonical win32-x64 and darwin-arm64 payload records from the **same UAR source revision** with their normal checksum/source checks. Existing immutable public input rules are preserved. This is a **task specification**, not a claim that the overlay, command repair or CI refusal exists today.

### Minimum local delivery receipt

| Field | Required meaning |
| --- | --- |
| Delivery and coverage | Delivery ID, complete user journey, original C01–C18 requirement/task mappings, owner and exact file claims. |
| Source freeze | Clean Boss commit, clean UAR commit, skill/payload revision if used, app version/profile, freeze time; record later repairs as a new exact snapshot. |
| Payload/package | Local-only versus canonical source clearly labeled; UAR archive and executable SHA-256, architecture, physical packaged path, DMG/app path and SHA-256. |
| Gate/runtime | One completed-phase integration gate outcome; exact `pnpm build:mac:arm64` outcome; opened app version; packaged UAR source/version, effective port and capability/health; actual UI action, state result, applicable restart and two-workspace isolation. |
| Evidence status | Separate `source`, `compiled`, `integrated`, `local-installed/functioning`, `published`, and per-platform `installed-accepted` states. Never promote one state by inference from another. |
| Time | `startedAt`, `sourceFrozenAt`, `localReadyAt`, actual gate/build durations, waiting/blocker intervals, aggregate active agent minutes when observable, and overrun reason. Unknown effort remains null. |
| Follow-up | Operator publication choice with timestamp or `pending`; platform targets and known support gaps; link to Karpathy boundary event/local receipt without inventing a second task ledger. |

`localDeliveryElapsed = localReadyAt − startedAt`. It includes all pre-delivery waits, compiler/build/gate time and retries, and is the clock for the **target** of one useful local delivery per elapsed hour. A cold first build may exceed that hour. If the app is not functioning at the hour boundary, report the actual elapsed overrun and the five evidence statuses; do not rename incomplete work as an hourly delivery. Summed active agent effort is a separate measure, not a substitute for elapsed delivery time; commit timestamps and the historical Karpathy `elapsedHours: 0.0` event do not measure it.

## Decision after every successful local delivery

Ask the operator exactly: **“Publish this version for all macOS and Windows targets now, or wait until the next delivery?”** The question follows a functioning local app, not merely a green package step. No answer leaves publication pending. A “wait” choice retains the working local artifact and does not imply rejection of its local acceptance. Independent later work may proceed on another source/output snapshot while the publication choice is pending; no site or release mutation is inferred from silence.

“All macOS and Windows” means **darwin-arm64, darwin-x64, win32-x64 and win32-arm64** with UAR enabled and the completed journey present. **No Linux** artifacts or links are part of this cadence. Current UAR-enabled build evidence covers only Apple Silicon and Windows x64; Mac Intel and Windows ARM64 are explicit missing production payload/profile work. If the operator selects “publish now” while one of four is missing, record that platform as blocked, complete its native implementation/build and retain the previous working public link until its replacement is valid. Never advertise a non-UAR installer as satisfying a UAR delivery, and never describe two platforms as “all four.”

## Full publication acceptance after “publish now”

1. **Freeze one release input.** Bind the selected delivery's clean Boss/UAR/skill source revisions, release version, UAR-enabled profile and exact native payload checksums. Canonical manifests for the required paired UAR records must name the same UAR SHA. Native jobs may finish independently, but each installer states its own actual source revision and signing status. No local-only overlay enters CI or a public release.
2. **Build the four native targets.** Produce Apple Silicon and Intel macOS installers and x64 and ARM64 Windows installers containing the intended UAR payload and UI journey. Confirm each resulting artifact's architecture, version, byte size and SHA-256. Signing is reported accurately, including unsigned status; a failed target remains failed rather than borrowing another architecture's pass.
3. **Publish through GitHub Releases.** Upload the exact installers to The Boss repository's release. For each target, retain an immutable manifest row with source commit(s), version, OS/architecture, artifact filename, size, SHA-256, signing status and exact GitHub download URL. Verify URL response and downloaded bytes against the recorded size/hash before replacing an advertised link. IPFS is not a publication target.
4. **Commit release metadata.** Merge completed platform rows without overwriting a newer successful row or erasing pending/previous links. Update `RELEASES.md` and the release manifest from the actual artifacts; commit and push The Boss release metadata. A single metadata publisher serializes platform merges and refuses an older job that would regress the published version.
5. **Update the website from that release.** Sync the existing `Know-Me-Tools/boss-landing-spot` repository's generated release data from the committed manifest, commit and push it, then publish the connected **The Boss Landing** Lovable project to [the-boss.know-me.tools](https://the-boss.know-me.tools). Confirm the live version and each advertised platform URL, and download/check bytes or a trustworthy exact-content equivalent for the live links. The website must point to the new GitHub installers only after those artifacts are valid. Keep each prior complete platform URL advertised until its replacement passes these checks.
6. **Record installed acceptance separately.** Publication plus URL/hash checks are not an installed operational result. Record Windows x64, Windows ARM64, Apple Silicon and Intel macOS launch/UAR/journey acceptance independently when observed; retain any pending status truthfully and repair a demonstrated failure against a new exact source/artifact revision.

`publicationElapsed = publicationFinishedAt − publicationStartedAt`, including queue, build, upload, operator and deployment waits. `endToEndElapsed` spans `startedAt` to final selected publication completion, or stops at `localReadyAt` while publication is deferred. Record overlapping work as separate intervals rather than summing it twice. This keeps local hourly delivery time distinct while exposing the full time to a downloadable and installed release. A publish-now decision does not weaken the four-platform acceptance criteria or permit a stale site update.

## Responsibility and lifecycle boundary

The parent D1 shipping owner implements the exact Mac command and payload/profile repair with Boss/UAR product owners, then runs its complete functional gate and local build. The later native platform track implements missing Intel/ARM support. One release owner publishes exact artifacts; one metadata/site publisher updates GitHub and the landing site. The read-only delivery observer can report elapsed, blocked and rework time but cannot authorize testing, publication, scope changes or KBD completion. Root KBD lead records canonical stage/plan decisions and retains C08 source/gate work with its current owner; dependency-ready C09 can advance independently.

This child process task is satisfied when the contract is explicit and traceable. The child does **not** produce a functioning DMG, release row, site deployment or installed acceptance; those remain parent product and release obligations after the approved child is reflected and its parent waypoint restored.
